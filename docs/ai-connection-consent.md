# AI connection consent foundation

This is the first delegated-authorization increment. It provides durable consent,
current permission evaluation and owner-only management APIs. It does **not** issue
tokens, implement the OAuth authorization-code flow, expose MCP tools or add the
frontend connection page. A consent record ID is never an authentication credential.
The existing web Principal still rejects MCP/worker identities.

## Decisions and API

Use a server-managed client catalog for the initial pilot. `ai_clients` is global
configuration with a stable ID, display name, enabled flag and allowed read scopes.
Only an operator can change it; the web runtime can only read it. The migration
creates an empty catalog. No AI vendor or callback is silently enrolled.

The existing CRM bearer authentication protects these endpoints:

| Endpoint | Behavior |
| --- | --- |
| `GET /api/ai-connections/clients` | Approved clients, available read permissions, 30-day consent lifetime and `tokens_available: false`. |
| `POST /api/ai-connections/preview` | Takes `client_id` and an explicit scope list; returns server-owned client identity, permissions and resource for consent presentation. No write. |
| `POST /api/ai-connections/consent` | Takes the same fields plus boolean `approved: true`; creates an immutable owner-bound record. Returns 201 with no credentials. |
| `GET /api/ai-connections?page=1&per_page=20` | Owner's bounded, paginated consent history; maximum page size 50. |
| `DELETE /api/ai-connections/{id}` | Idempotent, terminal revocation; preserves consent history. Foreign and absent IDs return the same 404. |

Supported scopes are `clients:read`, `leads:read`, `projects:read`,
`interactions:read` and `reports:read`. Reports additionally require a current admin
role. All permissions remain subject to the same record rules as CRM services.
Write, file, import, user-administration and platform-operation scopes are rejected.
Every response generated by the adapter carries `Cache-Control: no-store`.

The service rejects client-supplied owner/tenant IDs and implicit approval. A grant
binds the current user, tenant, registered client, exact scope set and configured
HTTPS `MCP_RESOURCE_URI`. It expires after 30 days. New approval is required to
change scopes or expiry. Limits are 20 unrevoked/unexpired records and 100 approvals
per rolling day per owner; a PostgreSQL user-row lock serializes creation across
processes. Revocation remains available at the limit and for disabled clients.

`require_permissions` is an internal stored-consent check, not token validation.
After a future OAuth adapter authenticates a token, it must match that token's
client, resource, owner and grant before calling this check. It reloads the grant,
current user/tenant activity, client activity/allowed scopes and database roles.
Expiry, revocation, role removal, client disablement or scope removal take effect
on the next evaluation. It returns only the required permission set, never a web
Principal; tool-level scope and record checks are still required. `last_used_at`
remains empty until an actual authorized MCP invocation is implemented.

## Database boundary and migration

`ai_connections` adds the fifteenth RLS-protected table. Its policy requires both
transaction-local `crm.tenant_id` and `crm.user_id`; settings are cleared/rebound on
every transaction, including pooled connections and authentication bootstrap. A
same-tenant admin cannot read another user's consent. An explicit composite owner
foreign key prevents cross-tenant membership even for an operator. The runtime
cannot delete consent history or change the client catalog. A database trigger
rejects edits to grant identity, scope, resource, creation/expiry and any attempt to
change an existing revocation timestamp. Re-consent creates a new record.

Migration `ai_consent_grants` follows `parent_link_rules`. Table creation, constraints,
grants, forced RLS, trigger and version advancement are one transaction. The staging
operator runner supports a rollback-only rehearsal and `--apply`; it requires the
known staging database, restricted runtime role and reviewed predecessor. No default
privileges or public registration are added. For a fresh installation, apply this
revision after the earlier runtime-role/RLS preparation; that earlier role-provisioning
script deliberately continues to grant only its historical table inventory.

The isolation inventory now covers **19 models/tables**, **15 protected tables** and
**21 policies**. Fault-injection coverage expands to 60 policy faults. Separate
tests cover actual migration/rollback, immutable history, same-user pool reuse,
foreign/absent responses, inactive identities, stale roles, scope/resource/client
mismatches, owner limits and concurrent creation.

## Next authorization increment

Integrate a standards-based authorization server (the existing Authlib dependency
provides protocol building blocks) and the user-facing consent flow. The browser
flow must use a server-bound authorization intent, PKCE S256, exact registered
redirects and explicit user approval; this CRM API alone is not that flow. Add
discovery, short resource-bound tokens, refresh rotation/replay handling and token
revocation tied to these owner grants. Do not advertise OAuth metadata before the
required endpoints work. Review/update the pinned Authlib version for that integration.

References: the [MCP authorization specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx)
defines the resource/authorization-server boundary; [OAuth security best practices](https://www.rfc-editor.org/rfc/rfc9700.html)
cover authorization-code and token protections. The initial pre-registered pilot
avoids an arbitrary-URL client fetcher; broader client metadata discovery and its
SSRF protections require a separate implementation. Distributed tool/token rate
limits, durable invocation auditing and the connection-management UI remain open.

## Validation and rollout

CI, migration rehearsal and staging evidence will be recorded after validation.
No production/frontend deployment or platform worker changes. Application rollback
target is staging v36 `898cc7a17b604502b95568f45e7b375048ee8702`; the additive tables
may remain safely in place when rolling back the app. Never erase consent history
as part of application rollback.
